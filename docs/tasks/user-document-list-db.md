# 사용자 문서 목록 API를 DB 기준으로 변경

## 과제 목적

사용자용 `GET /api/v1/documents`의 목록 조회 기준을 AI 서버에서 미들웨어 DB로 변경한다. 이 과제를 통해 HTTP 요청이 라우트, 인증·DB 의존성, 서비스, ORM 모델, 응답 스키마를 거쳐 반환되는 흐름을 파악한다.

이번 과제는 **문서 목록 조회 경로**에 한정한다. DB와 AI 서버 간 상태 불일치, 적재 상태 갱신 방식 등 변경으로 드러나는 추가 문제와 그 해결책은 별도 과제로 다룬다.

## 현재 구조 파악

아래 코드를 읽고, 사용자 API와 관리자 API의 요청부터 응답까지의 흐름을 각각 정리한다.

| 확인할 곳 | 살펴볼 내용 |
| --- | --- |
| [`app/api/v1/routes/document.py`](../../app/api/v1/routes/document.py) | 사용자 목록 엔드포인트, 인증, 쿼리 파라미터, 응답 모델 |
| [`app/services/document_service.py`](../../app/services/document_service.py) | 현재 AI 서버 목록 호출과 관리자용 DB 조회 방식 |
| [`app/api/v1/routes/admin.py`](../../app/api/v1/routes/admin.py) | 관리자 문서 목록 엔드포인트와 서비스 호출 |
| [`app/models/document.py`](../../app/models/document.py) | DB 컬럼, 프로젝트 문서 구분, 원본 파일의 지연 로딩 |
| [`app/schemas/document.py`](../../app/schemas/document.py) | 사용자용과 관리자용 응답 필드의 차이 |

현재 사용자 API는 AI 서버의 `/documents` 응답을 전달하고, 관리자 API는 `documents` 테이블을 조회한다. 두 API 모두 `domain`과 `offset`·`limit`을 받는다.

## 변경 후 조회 정책

두 목록은 모두 DB의 `documents` 테이블을 기준으로 조회한다. **조회 정책은 어떤 문서 행을 결과에 포함할지 정하는 조건**이다.

| 조건 | 관리자 목록 `GET /api/v1/admin/documents` | 사용자 목록 `GET /api/v1/documents` |
| --- | --- | --- |
| 문서 범위 | `project_id IS NULL`인 전사 공용 문서 | 동일하게 전사 공용 문서만 |
| 적재 상태 | 상태 조건 없음: `pending`, `queued`, `running`, `done`, `error` 등을 모두 포함 | `status = 'done'`인 문서만 포함 |
| 도메인 | `domain` 요청 시 해당 도메인만 포함 | 동일 |
| 문서명 검색 | `search` 요청 시 이름에 해당 문자열이 포함된 문서만 포함 | `search` 파라미터 없음 |

예를 들어 전사 공용 HR 문서가 `done` 8건, `running` 2건이면 `domain=HR` 요청에서 관리자는 10건, 사용자는 8건을 대상으로 페이지를 구성한다. 프로젝트에 속한 문서는 상태와 관계없이 두 목록에서 제외한다. `total`도 각 목록의 조건을 적용한 전체 건수다.

관리자 조회는 업로더 정보를 함께 읽고 응답에 상태 등을 표시한다. 사용자 응답의 필드가 다른 것도 사실이지만, **업로더 정보 로딩과 응답 필드 차이는 위 표의 문서 포함 조건과 구분**한다.

## 1차 산출물: 구현 전 설계안

코드를 수정하기 전에 다음 내용을 짧은 문서나 표로 정리해 리뷰받는다.

1. 사용자 API의 기존 요청·응답 계약과 변경 후 계약. URL, 인증, `offset`, `limit`, `domain`, `total`, `has_more`의 유지 여부를 명시한다.
2. 조회 대상과 필터 조건. 사용자 목록에는 프로젝트 참고 파일을 제외하고 `status='done'`인 전사 공용 문서만 포함한다. 관리자 목록은 현재처럼 상태와 관계없이 전사 공용 문서를 조회한다. 이 차이가 목록과 `total` 조회에 각각 어떻게 반영되는지 설명한다.
3. 사용자 응답 필드와 DB 컬럼의 대응표. 특히 기존 응답의 `type`, `owning_department`, `applied_at`은 DB 컬럼과 이름 또는 의미가 그대로 일치하지 않는다. 대응할 수 없는 필드를 임의로 다른 의미의 값으로 채우지 않는다.
4. `total`, 정렬, `offset`·`limit`, `has_more` 계산 방법. `total`을 세는 쿼리와 실제 문서 목록을 가져오는 쿼리가 같은 조회 조건을 사용해야 한다. 예를 들어 `domain=HR`로 요청했다면, `total`도 HR 문서만 세고 목록도 HR 문서만 반환해야 한다.
5. 관리자용과 사용자용 조회의 공통점과 차이. 위 표에서 실제 문서 포함 조건인 `status='done'`과 선택적 `search`를 확인한다. 업로더 정보 로딩과 응답 필드는 조회 정책과 구분한다. 사용자용 조회 함수를 별도로 두되, 공통 DB 조회 부분을 공유할 필요가 있는지 판단한다. 변경할 파일과 각 파일의 역할을 정리한다.

리뷰에서는 **`done`인 전사 공용 문서만 사용자 목록에 나오는지**와 **응답 스키마를 어떻게 정의할지**를 먼저 확인한다.

## 2차 산출물: 구현

설계안 리뷰 후 다음 범위에서 변경한다.

- 사용자 목록 라우트가 DB 세션을 받아 서비스의 DB 조회 결과를 반환하도록 수정한다. 목록 조회 중 AI 서버로 HTTP 요청을 보내지 않는다.
- 서비스에 사용자용 조회 함수를 두고 `project_id IS NULL`, `status='done'`, 요청받은 `domain` 조건으로 목록과 `total`을 구한다. 관리자용 조회와 공통 DB 조회 부분을 공유할지는 중복 정도를 보고 결정한다. `total`은 현재 요청 조건에 맞는 문서의 전체 개수이며, 목록은 그중 `offset`부터 `limit`개만 가져온 결과다. 목록 조회에서 원본 파일 바이너리 `data`를 읽지 않는다.
- 확정된 필드 대응표에 따라 사용자 응답 스키마와 변환 코드를 수정한다. 관리자 전용 정보가 사용자 응답에 포함되지 않도록 확인한다.
- 정렬 기준을 명시하고 페이지네이션 응답을 구성한다. API 설명과 README의 문서 목록 예시도 실제 동작에 맞춘다.

현재 모델에 조회용 컬럼이 이미 있는지 먼저 확인한다. 필요하지 않은 DB 모델 변경이나 마이그레이션은 과제 목표가 아니다.

## 완료 확인

- AI 서버의 목록 API를 호출하지 않아도 사용자 문서 목록을 조회할 수 있다.
- 프로젝트 참고 파일이 사용자용 전사 문서 목록에 섞이지 않는다.
- `domain` 필터, 첫 페이지, 다음 페이지, 마지막 페이지에서 목록과 `total`·`has_more`가 일관된다.
- 응답이 확정된 스키마를 따르고, 원본 파일 바이너리와 관리자 전용 정보가 노출되지 않는다.
- 기존 사용자 인증과 `offset`·`limit` 입력 제한이 유지된다.

## 별도 과제로 남길 항목

DB에 기록된 적재 상태와 AI 서버의 실제 상태가 달라지는 경우에는 실제 색인이 끝난 문서도 `done` 필터에 걸리지 않아 사용자 목록에서 빠질 수 있다. 이 상태 동기화 문제, 색인 완료 시각의 저장 여부, 기존 데이터와 AI 서버 색인의 불일치 처리는 이번 과제에서 해결하지 않는다. 설계 또는 구현 중 발견한 사례는 후속 과제로 기록한다.
