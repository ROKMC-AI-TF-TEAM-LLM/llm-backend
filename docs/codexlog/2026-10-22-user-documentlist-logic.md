## 무엇이 달라졌나

기존에는 사용자 목록이 AI 서버의 벡터스토어를, 관리자 목록이 DB를 조회했다. 이제 두 목록 모두 백엔드 DB의 `documents` 테이블을 조회한다.

사용자 목록 `GET /api/v1/documents`의 조건은 다음과 같다.

- `project_id IS NULL`: 전사 공용 문서만 조회한다.
- `status = 'done'`: DB에 색인 완료로 기록된 문서만 조회한다.
- `domain`을 요청하면 해당 도메인만 조회한다.
- 등록 시각 내림차순으로 정렬하고, 같은 시각이면 문서 ID 내림차순으로 정렬한다.
- 목록과 `total`에 같은 조건을 적용한다. `total`은 페이지 크기와 무관한 전체 해당 건수이며, `has_more`는 `offset + 반환 문서 수 < total`이다.

예를 들어 전사 HR 문서가 `done` 8건, `running` 2건이면 관리자는 10건, 사용자는 8건을 대상으로 페이지를 구성한다. 프로젝트 문서는 두 목록에서 모두 제외된다.

## API와 응답 필드

URL, 사용자 인증, `offset` 기본값 0, `limit` 기본값 20 및 허용 범위 1~100, `domain`, 응답 래퍼와 페이지 정보는 유지했다. 응답 필드의 이름도 유지했다.

| 사용자 응답 필드 | DB 대응 및 처리 |
| --- | --- |
| `name` | `Document.name` |
| `domain` | `Document.domain` |
| `visibility` | `Document.visibility` |
| `owning_department` | `Document.department` |
| `type` | 같은 의미의 컬럼이 없어 `null` |
| `applied_at` | 같은 의미의 컬럼이 없어 `null` |

`type`을 MIME인 `content_type`으로, `applied_at`을 등록 시각인 `created_at`으로 대체하지 않았다. 프론트엔드에서 이 두 필드로 파일 종류나 날짜를 표시한다면 빈 값 처리가 필요하다. 파일 종류를 다시 제공하려면 응답의 의미와 변환 규칙을 정하는 후속 작업이 필요하다.

사용자 목록 쿼리는 응답에 필요한 컬럼과 문서 ID만 읽는다. 원본 바이너리, 업로더 관계, 색인 작업 정보는 읽지 않으며 사용자 응답에도 노출하지 않는다.

## 알아둘 제한과 후속 과제

1. **상태 자동 동기화는 아직 없다.** 현재 상태 조회 API를 호출해야 AI 작업 상태가 DB에 반영된다. 실제 색인이 끝났더라도 DB가 `queued`/`running`이면 사용자 목록에서 빠진다. 업로드 후 목록이 비어 보인다면 DB 상태와 관리자 상태 조회 동작을 먼저 확인해야 한다.
2. **DB와 벡터스토어의 기존 불일치를 복구한 것은 아니다.** 벡터스토어에만 있는 문서는 목록에 나오지 않는다. 반대로 DB가 `done`이면 실제 색인이 없어도 목록에는 나온다. 상태 갱신 정책과 기존 데이터 대조·복구는 별도 작업이 필요하다.
3. **미리보기는 구현하지 않았다.** 기존 다운로드는 이름으로 최신 등록본을 찾는다. 같은 이름의 문서가 여러 개 있으면 목록의 특정 행과 다운로드 결과가 달라질 수 있다. 향후 미리보기에는 문서 ID 기반 접근을 검토하는 편이 좋다.

이번 변경의 범위는 사용자 문서 목록의 조회 기준을 DB로 통일하는 데 한정했다.
